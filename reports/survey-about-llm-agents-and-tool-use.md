# LLM Agents and Tool Use: Paradigms, Evaluation, and Reliability

## TL;DR
- Tool-using agents turn language-model outputs into external actions and then condition later decisions on returned observations; the core design choice is where tool choice and control live—in prompting-time interaction, learned API-call behavior, or an orchestration/search layer. [1][2][3]
- Progress has shifted from demonstrating reasoning/action loops to scaling tool inventories, training call behavior, and improving retrieval; gains depend on API documentation, data quality, and evaluation design rather than tool-call syntax alone. [4][5][6]
- Evaluation is moving beyond static single-turn calls toward simulated, stateful, multi-step and conversational settings, but simulation, model-based judging, changing APIs, and benchmark-specific task design remain important caveats. [7][8][9][10]
- Stronger planning and longer context do not remove operational risks: ambiguous instructions can produce unsafe actions, long-horizon tasks stress memory and dependency tracking, and multi-call systems should be assessed for cost and latency as well as task success. [11][12][13][14]

## Background
An LLM agent using tools is a system in which a model selects or generates calls to external capabilities—such as search, APIs, or software functions—receives tool outputs, and uses those observations to continue toward a user goal. This differs from ordinary text generation because correctness depends not only on the model's answer but also on tool selection, argument construction, call ordering, interpreting returned state, and deciding whether more action is needed. The literature consequently treats tool use as a pipeline: retrieve/choose a tool, plan or decompose the task, execute a call, and incorporate results. [1][15][3]

Tool use matters because it can connect a model to external knowledge and actions, while introducing interfaces and state that the model must handle reliably. ReAct made the interaction loop explicit: interleave reasoning and actions, observe the environment, then update the next step. Toolformer instead learned when to insert API calls using a self-supervised procedure that retained calls when their results improved future-token prediction. These foundational approaches illustrate a lasting distinction between inference-time interaction policies and tool behavior learned during training. [1][2]

## Paradigms: prompting, learning, and orchestration
ReAct presents tool use as an observable reasoning/action/observation trajectory. In its experiments a frozen PaLM-540B model used human-written few-shot trajectories; the paper reports that one- or two-shot ReAct exceeded imitation- or reinforcement-learning baselines by 34 and 10 absolute success-rate points on ALFWorld and WebShop, respectively. Those results are tied to the paper's tasks and setup, not a general comparison across modern agents. The authors also note that large action spaces can require more demonstrations than fit comfortably in context. [1]

Toolformer moves part of the decision into model training: sample candidate API calls, execute them, filter for calls that improve later-token prediction, and fine-tune on the retained sequences. This avoids requiring task-specific reasoning traces at inference in the same way as ReAct, but its demonstrated setup assumes text-compatible I/O and a handful of examples for each API. [2]

A third family makes APIs and task workflows first-class. API-Bank separates planning, API retrieval, and calling; Gorilla couples API instruction tuning with retrieved documentation; and ToolLLM combines synthetic instructions and solution paths with API retrieval and search over candidate reasoning traces. Their emphasis is less on exposing a free-form thought/action trace and more on choosing the right interface, respecting its schema, and executing a valid sequence. This division of labor also makes failures diagnosable: a bad outcome can arise from retrieval, planning, arguments, or execution rather than from one undifferentiated “reasoning” capability. [4][5][15]

Recent work addresses distinct bottlenecks rather than replacing a single canonical agent design. ToolACE is described by its Hugging Face paper record as a function-calling data-synthesis approach intended to create diverse tool-learning data for smaller LLMs. AsyncLM, by contrast, changes execution semantics: it allows function calls and model generation to proceed asynchronously, and reports 1.6×–5.4× lower completion latency than synchronous calling on its BFCL task set. The ToolACE record is a short summary, and AsyncLM's speedups are benchmark-scoped; neither establishes general superiority across agent workloads. [6][16]

## Training and tool access at scale
The shift from small tool sets to large, changing catalogs puts retrieval and documentation quality at the center. Gorilla is a fine-tuned LLaMA-based model for API calling; its authors report that it surpasses GPT-4 on writing API calls and substantially mitigates hallucination in their API-call evaluation. [4]

ToolLLM scales data construction around 16,464 real-world REST APIs in 49 categories, using generated single- and multi-tool instructions and solution paths; it pairs the fine-tuned ToolLLaMA with a neural retriever and uses a depth-first search procedure to explore reasoning traces. This supports evaluation of generalization to unseen APIs, yet data generated by an LLM and a changing live API environment create their own validity problems. The approach therefore expands tool coverage and search while inheriting dependence on generated trajectories, retriever quality, and evaluator assumptions. [5]

Supervised API-use datasets and synthetic data are not the only route. Toolformer uses self-supervision, while more recent environment-tuning work reports learning from 400 BFCL problem instances with structured curricula, actionable feedback, and progress rewards. That paper reports competitive in-distribution results and stronger out-of-distribution generalization than its tested baselines; the evidence remains limited to its comparisons and should not be generalized to all tools or environments. Across these approaches, the open design question is not simply how to generate more calls, but how to ensure that training examples and feedback reflect changing interfaces, multi-step state, and robust behavior on imperfect requests. [2][10]

## Evaluation: from calls to interactive tasks
Early benchmarks help decompose the problem. API-Bank evaluates planning, retrieval, and API calls and supplies a runnable set of 73 tools, 314 test dialogues, and 753 API calls. Its decomposition is useful precisely because success on a well-formed call does not demonstrate the ability to select a tool or plan a sequence. Reported scores should not be read as directly comparable to benchmarks with different tasks and construction. [15]

Large-scale real-API testing creates reproducibility problems. StableToolBench identifies instability in online API status and proposes a virtual API server with a caching system and API simulators to address changes in API status. Hugging Face's record likewise summarizes its use of a virtual API server and caching to address real-API instability. [7][17]

Newer evaluations broaden what “tool use” means. ToolSandbox evaluates stateful tool execution, implicit dependencies, user interaction, and intermediate as well as final milestones. SEAL organizes evaluation around retrieval, API calls, and final responses, using standardized tasks and simulated API responses. ACEBench includes ambiguous/incomplete instructions and multi-agent dialogue; its authors report that most tested models scored below 50% end accuracy on its Agent tasks. These are complementary benchmark designs, not one universal leaderboard: their distinct environments measure different aspects of interaction and reliability. [8][9][18][19]

The newest benchmark designs emphasize multi-step control and robustness. FuncBenchGen uses hidden function-dependency DAGs to vary dependency depth and distractors; its experiments report declining success as dependency depth increases and highlight stale or incorrectly propagated arguments as a failure mode. The authors report that restating prior variable values at each step raised GPT-5 success from 62.5% to 81.3% on their setup. This is evidence for explicit state tracking in that synthetic environment, not a demonstrated fix for live heterogeneous APIs. [10]

## Planning, memory, and safety in deployment
Complex tool use is a planning and state-management problem as much as a function-calling problem. PlanningArena evaluates single-application, cross-application, parallel, chained, and DAG-style workflows and reports that tested models degrade as complexity rises, including missing subtasks and incorrect dependencies. HiAgent addresses long-horizon context by grouping work into subgoals, summarizing completed chunks, and retaining relevant action-observation history; across five long-horizon tasks it reports a twofold success-rate increase over its stated baseline. Both studies point to the value of structured state, but their results are specific to their tasks and baselines. [12][13]

Safety evaluation exposes risks that ordinary success metrics may miss. ToolEmu uses an LM-emulated sandbox and evaluator to test ambiguous or underspecified requests across 36 high-stakes toolkits and 144 cases. The paper reports that 68.8% of failures identified by the system were validated as real-world agent failures by humans; even the safest tested agent had evaluator-identified failures in 23.9% of benchmark cases. These numbers describe that benchmark and its threat model, not real-world deployment failure rates. Emulation makes diverse risky scenarios easier to test, but does not guarantee that every tool behavior is reproduced accurately. [11]

Finally, agent quality is multi-objective. A system that calls tools repeatedly may improve task success at the cost of latency and money; an analysis of agent evaluation recommends considering cost alongside accuracy and discusses latency as another objective. In its HotPotQA experiments, joint accuracy-cost optimization reduced variable cost by 53% for GPT-3.5 and 41% for Llama-3-70B while maintaining similar accuracy relative to default DSPy implementations. These results are task- and price-specific, but they underscore why comparisons should account for tool/API charges, inference calls, and runtime rather than ranking systems only by final-answer accuracy. [14]

## Trends and open problems
The field is moving from isolated demonstrations of tool calls toward end-to-end agents evaluated on retrieval, planning, state transitions, multi-turn interaction, safety, and operating cost. One trend is greater explicitness: decomposing tool-use into subtasks, representing dependencies, validating intermediate outcomes, and tracking state rather than treating a call as a one-off text completion. Another is a shift in where complexity sits: learned call policies and synthetic training data can reduce reliance on hand-written trajectories, while retrieval and orchestration systems manage large tool catalogs and execution constraints. [5][15][8][12][3]

Several gaps remain. First, benchmark comparability is limited: live APIs change, simulations improve stability but may depart from real behavior, and model-based evaluators can reproduce evaluator bias. Second, robust generalization to ambiguous user intent, stale or missing state, changing schemas, and unseen dependencies remains unsettled. Third, safety coverage needs to extend beyond the underspecified high-stakes cases represented by current emulation benchmarks. Finally, evidence is needed on combined task success, reliability, cost, and latency in representative settings; the available papers offer task-specific findings rather than a unified controlled comparison of agent architectures. [7][8][9][18][10][11][14]
